Shepherd — how it works

An agent orchestration engine built as a Herdr plugin: one supervisor process, a declarative pipeline engine, and step scripts in whatever language you like. This is what the first four milestones actually do, with a worked example taken from a real run.

shep 0.1.0 · herdr 0.8.0 · socket protocol 19 · 2026-08-18 · M1–M4 built · PLAN.md · NOTES.md

Two sentences that determine the design

The engine decides nothing a human didn't write down

Every branch comes from config. engine/plan.rs is pure — config plus a task row in, one decision out. It has no clock, no I/O and no LLM. The Rust binary has no API client at all.

Nothing is asked of a worker agent

Herdr reports when an agent stops, and lint, tests and review catch bad work without its cooperation. An agent is never trusted to report its own success.

Consequences you can see in the code: a step script that exits non-zero is an error no matter what it printed, and a check is a verdict about a specific commit sha that shep stamps rather than the submitter.

The Herdr edge — four manifest hooksappending
pane.agent_status_changed
The one that matters: an agent going done.

The endings where an agent stops without Herdr ever calling it done.
workspace.closed added
Not in the plan. Probing found that closing a workspace fires neither pane hook for the panes it takes with it.
hooks/forward.sh appends the raw event and exits — it decides nothing. The status payload has no previous-status field, so working out the working → done edge needs memory, and a hook holding memory of its own would be a second source of truth. Consuming these to resolve a deferred step is M5.

There is no IPC

The CLI and the supervisor are the same binary over the same file. A command is a transaction; the supervisor notices on its next poll. That is the entire mechanism — no socket, no protocol, no server.

# terminal 1                        # terminal 2 (or Herdr's [[startup]])
$ shep create --type check "…"       $ shep supervise
  INSERT task + event                  …polls, sees it ~200ms later…
  t-1                                UPDATE task SET status='running'

What this buys

  • Every read command works with the supervisor down
  • Errors surface from the command instead of round-tripping
  • Consistency comes from shared code, not a transport

What it costs

  • Task creation is picked up on the next poll — ~200ms
  • Both sides are writers, so every transition must serialise
  • One machine, one Herdr session

What would bring IPC back

  • Wanting the supervisor somewhere the CLI isn't
  • Wanting to push to long-lived subscribers instead of having them poll

The five words

WordMeaningWhere it lives
taskOne unit of requested work: a brief, a type, and a position. task row
typeA named composition of pipelines — feature, hotfix. No loops, so termination is obvious. The only thing an agent chooses, which is why description lives here and nowhere else. [type.x]
pipelineA small state machine over steps. Owns its own loop and round cap. Returns an outcome, which is why a pipeline can be used as a step. [pipeline.x]
stepOne script invocation. lint → .shep/scripts/lint.sh.a file
checkA verdict plus evidence about a specific commit. Written by linters, test runs, reviewing agents and humans alike.check_run row
Round is scoped to the innermost pipeline. "Round 2 of review" is meaningful; "round 2 of feature" is not. Because the task row records one round, and records its position by name, three things had to become validation errors: a step name repeating in a pipeline, a pipeline name repeating in a type, and a looping pipeline nesting another.

Out — the last line of stdout

{"outcome":"pass","note":"79 tests passed"}
{"outcome":"reject","note":"2 lint errors"}
{"outcome":"started","pane":"wA:p2"}

# Only the LAST line is the answer.
# Everything above it is logs, so a script
# is free to shell out to pytest or
# claude -p and let it print.
OutcomeWhat the engine doesResulting state
passAdvance. Next step, or next pipeline, or finished.queued at the next position
rejectTake the pipeline's on_fail. With none, there is nowhere to go. on_fail loop is M6 parked
startedA promise, not an answer: resolve later per the pipeline's await. resolution is M5 running, awaiting
errorPark the task, with the reason on the event.parked
A non-zero exit, or an unparseable last line, is an error regardless of what was printed. A script that failed and still claimed to pass is exactly the case worth not believing — there's a test for it.

Status, and why there are only five

queued→ running→ queued→ running→ finished · parked · cancelled

The invariant that earns its keep

  • queued — ready to run its next step, position already written
  • running — a step is in flight right now
  • parked — the engine could not decide; inert until shep retry

A task never sits in running between steps, which is what makes the next card possible.

Recovery, on the strength of that

  • A task in running with no bound pane was synchronous and got orphaned when the supervisor died → re-queued on startup
  • A task in running with a bound pane has an agent still working in it → left alone
  • So a clean stop, a SIGKILL and a panicked step thread all recover the same way, and shutdown never has to wait on a pytest
There is no reconciliation loop. Completion is edge-triggered, and a stuck task sits there until you retry it. That is accepted because the failure is inert — nothing is corrupted by waiting, and shep trace says why.

What isn't built yet

The worked example above is the whole of the synchronous path. Everything that makes this more than a batch runner is still ahead.

AddsDone when
M5 Deferred steps with a pane: worktree create, pane split, shep bind-pane, agent start, resolution off the status event via check_run, shep context resolving from $HERDR_PANE_ID. An agent implements something unattended and the task advances on its own.
M6 The review loop: on_fail → fix → round + 1, max_rounds, on_exhausted, and check submit with sha stamping. A deliberately bad implementation loops twice, then exhausts.
M7 Handoff: await = "human", muting status events for a pane you own, shep approve / reject, running a pipeline out of band. You can converse with the agent through a whole handoff without the state machine moving.
M8 Integrate and teardown: rebase, merge, stale-check refusal, worktree removal. A feature task goes end to end with one rejection and one handoff.
M9 Visibility: sidebar badges via workspace report-metadata, a watch shep ps pane, keybound actions. You can tell what every task is doing from the sidebar alone.
Two spots where the current behaviour is a placeholder rather than a decision: a reject in a pipeline that has an on_fail parks instead of looping (M6), and a started outcome in a pipeline that has an await records the promise but nothing yet resolves it (M5).

Three things Herdr taught us on the way

Workspace close is invisible

Closing a workspace fires neither pane.closed nor pane.exited for the panes it takes with it. A task gets a workspace of its own, so that ending would have been invisible — hence a fourth hook on workspace.closed, whose payload gives a workspace_id and no pane id.

pane.exited lags

An exit in a pane produced the event 20–25 seconds later, and a pane whose workspace closed shortly after the exit never produced it at all. It is a backstop, not a trigger to design around.

pane report-agent is a test harness

herdr pane report-agent <pane> --state working fires a real status hook without running an agent, which makes the whole M5 path testable in about a second instead of a minute.

Unknown manifest fields are ignored silently and unknown event names only warn, so a typo yields a plugin that links cleanly and never fires. That is what scripts/verify-plugin.sh is for: it asserts on herdr plugin list --json.
